小地圖定位

本文只說明即時定位鏈路。路徑規劃、路線跟隨和遊戲輸入見網格導航。

1. 職責邊界

WorldPoseService 在首次讀取時懶建立，由執行器共享，支援兩個獨立位置源：

  • 視覺源：標定地圖匹配提供絕對 X/Z，里程計、區域性視窗和關鍵幀視覺錨定鏈約束相對位移；
  • 抓包源：可選後端直接提供角色 X/Y/Z、地圖、速度和朝向。

生產定位不再啟動或讀取官方地圖 WS、本地 WS，也不以抓包座標引導視覺搜尋。 物品導航、網格導航和滑索通過 RuntimeStateMixin.world_pose() 讀取 world.pose， 檢查可信狀態後再執行動作。視覺源不能測量真實高度，y=None，介面顯示“高度未知”。

2. 模組

模組 職責
position_service.py 選擇獨立位置源、處理幀時間、釋出統一契約
calibrated_map_store.py / map_set_locator.py 載入資源、在已安裝地圖中自動選擇地圖
minimap_map_locator.py ROI 掩膜快取、圖示排除、絕對匹配、自適應區域性搜尋和連續幀確認
layered_minimap_locator.py 將主圖與分層圖變換到相同世界座標並競爭樓層證據
visual_position_source.py 將標定地圖錨點與視覺位移鏈組合成獨立視覺源
capture_pose_mixin.py 抓包後端的生命週期、會話和座標可信狀態
wgc_frame_timing.py 將 WGC SystemRelativeTime 與具體 NumPy 幀關聯
runtime_state/world_pose.py 對外世界座標契約
data/official_map_client.py 可選設施資源的 HTTP 認證與查詢；與定位無關

minimap_position_mixin.py、ws_position_mixin.py 和舊融合器保留供歷史工具/測試使用， 不在生產 WorldPoseService 的繼承鏈中。物品導航也不再掛載舊版 WS 導航實現。

3. 資料流

flowchart TD
    FRAME[游戏原生客户端帧与呈现时间] --> MATCH[标定主图和分层图匹配]
    FRAME --> ODOM[视觉相对位移]
    MATCH --> CHAIN[局部窗口与关键帧视觉锚定链]
    ODOM --> CHAIN
    CHAIN --> SERVICE[WorldPoseService 选择的位置源]
    PACKET[可选抓包后端] --> SERVICE
    SERVICE --> HUB[RuntimeStateHub: world.pose]
    HUB --> ITEM[物品导航]
    HUB --> NAV[网格导航与滑索]

消費者按需請求取樣；沒有消費者時不會在後臺固定頻率截圖。切換來源、地圖或資源目錄， 修改視覺鏈配置、解析度變化和幀時間回退都會清空舊基準。切換源不融合兩個源的座標。

4. 座標系

4.1 世界系

  • 水平位置統一為 (x, z)，單位為米；
  • 朝向使用羅盤方位角：正北 0°、正東 90°、正南 180°、正西 270°；
  • 世界 +x 為東，世界 +z 為北。

4.2 地圖系

  • 影像座標使用 OpenCV 約定：x 向右、y 向下；
  • 小地圖紋理移動方向與玩家移動方向相反；
  • 相位相關得到內容位移 (dx, dy) 後，玩家地圖系位移為 (-dx, -dy)；
  • 軸對映負責把地圖系畫素轉換為世界米：
world_delta = map_to_world_px @ map_delta_px

5. 位置源

5.1 標定地圖與視覺鏈

全域性 Position Config 的 视觉地图资源目录 預設為 assets/nav-grid-data/localization/maps。 安裝資源時保留以下佈局，也可顯式指向另一個專案匯出的資源根目錄：

<root>/maps/map02/4/map02_4.png
<root>/maps/map02/4/map02_4_mapping.json
<root>/layers/catalog.json
<root>/layers/map02/.../<layer>.png

配置填寫 <root>/maps。生產程式碼沒有對開發機或相鄰倉庫路徑的隱式依賴，也不會下載資源。 標準資源包位於 nav-grid-data 子模組的 localization/ 目錄。原始碼安裝需初始化子模組並 拉取 LFS 內容：git submodule update --init -- assets/nav-grid-data，然後執行 git -C assets/nav-grid-data lfs pull。釋出同步流程會展開整個子模組，並通過 deploy.txt 中的 assets 條目包含地圖與分層資源；不依賴標註資源倉庫自動更新。 已有自定義目錄或仍存在的舊資源目錄保持原值；失效的舊預設目錄 assets/localization/maps 會在配置載入前備份並遷移至新的打包資源目錄。 地圖 PNG 尺寸必須與 mapping 的 image_size 一致。地圖 ID 留空時自動比較已安裝標定圖； Nav Config 指定地圖 ID 可縮小首次搜尋範圍。自動搜尋先比較主圖，只展開候選主圖的分層。 主圖證據不足時，每拍輪流探測一個分層；強候選隨後進入附近所有重疊分層的競爭。 當前搜尋範圍內的重疊分層會保留在快取中，移出範圍後再按記憶體目標淘汰，避免初始化迴圈淘汰。 首輪載入和解碼大型資源會較慢，超過兩秒的結果不會對外發布為可信座標。

首次定位和丟失後重新定位要求至少兩幀時間相鄰且空間一致的觀察，並滿足 robust NCC ≥0.85、 未裁剪 NCC ≥0.65、候選差距 ≥0.08。差距允許由完整環帶或魯棒證據給出，但所用證據必須 與所有其他候選都拉開差距，不能從不同候選各取一個有利分數。圖示排除掩膜由當前畫面獨立生成，至少保留 55% 環帶和 每象限 35% 環帶。圖示與環帶有任一重疊畫素即生成排除掩膜，不設覆蓋率啟用閾值。 白色設施圖示以亮白或彩色核心為種子，擴充套件到相連的淺色抗鋸齒邊緣，再按小地圖尺寸排除 黑色描邊。增強掩膜不滿足原覆蓋率或分佈紋理要求時，退回原掩膜；策略只由當前畫面決定， 不按候選匹配分數挑選掩膜，也不降低 NCC、候選差距或連續幀確認門檻。 魯棒評分相對未裁剪分數最多提高 0.20，限制相似地形的虛高候選。載入畫面、紋理不足、遮擋過多、過期幀或資源錯誤均拒絕釋出座標。 通過嚴格證據門檻、僅等待連續幀確認時，視覺源標記 visual_confirmation_pending。 網格導航在 WGC 呈現時間有效時立即請求下一幀，省去固定控制週期等待；同一呈現時間的 重複幀保留已有證據但不增加確認次數，並短暫等待最多 1/60 秒，防止空轉。 資源未齊、弱候選、無真即時間戳及抓包來源仍按原控制週期等待；確認幀數、最長幀間隔、 搜尋範圍和識別門檻均不改變。 區域性搜尋視窗按標定仿射矩陣換算世界米半徑，並在世界座標下過濾候選，避免非 4 px/m 或非等向標定縮小搜尋範圍。里程計未取樣時不重複加入快取環帶幀；新的絕對錨點仍可釋出。 區域性搜尋半徑隨幀間隔和最大運動速度擴大；弱證據先擴大區域性範圍，再回到全圖搜尋。

5.2 分層資源與樓層證據

與 nav-grid-editor 協作確認的 layers/catalog.json 當前使用 schema 1。 只將 map_category=layered 的圖層與對應 map_name 主圖共同定位；獨立場景不能僅憑歸檔目錄 推斷共享座標系，必須有自己的標定後再接入。圖層邊界按以下公式轉換：

X = west + u * (east - west) / width
Z = north - v * (north - south) / height

圖層會重取樣到 4 px/m，變換包含 OpenCV 畫素中心偏移。主層契約 ID 為 __main__。 視覺目錄 localization/layers/catalog.json 與導航層宣告索引是不同入口。導航從網格目錄 優先讀取 catalog.json，不存在時讀取資料倉的 levels.json；層 ID 須與網格後設資料的 tier 一致。目錄宣告不代表該層已有可走網格，缺少網格時仍須保留 no_grid 語義。 X/Z 相同但樓層不同的候選不能合併成一個樓層證據。樓層差距不足、相關資源缺失或目錄宣告 缺失樓層時，仍可接受有充分證據的水平位置，但必須釋出 tier_id=None、tier_trusted=False。 視覺源宣告 tier_evidence_required=True；網格導航在樓層未確認或沒有對應網格時拒絕猜主層。 抓包源有真實 Y，可繼續使用現有高度範圍和拓撲規則。不能把視覺未知高度補成零。

5.3 抓包直通（實驗技術）

另一條路完全繞開上面兩條：遊戲主 TCP 連線裡週期性上報主控角色的世界座標， 一個獨立的外部程式被動抓包並離線解密後，通過本地 HTTP 暴露同一個世界座標系的座標 ——與官方地圖 WS 逐位一致，並且額外自帶真實高度、朝向與速度。

後端程式的獲取與更新

exe 不再需要使用者手工放置：開啟「使用實驗技術」後由本應用從 luqing233/endfield-capture-backend 的 Release 下載，並在有新版時靜默更新。

點「啟動遊戲」前 阻塞補齊（缺了就下載/更新）。寧可啟動多等十幾秒，也不能讓遊戲先連上
點「檢查並更新後端」 手動觸發一次，忽略節流

安裝位置是 <应用目录>/downloads/capture_backend/。不能放 configs/：那裡的東西會被配置 匯出整個打包，而匯入側對單個成員硬性限制 16 MB（config_transfer_patch._MAX_IMPORT_MEMBER_BYTES）， 18 MB 的 exe 一旦進去，匯出的配置包就再也導不回來。downloads/ 已被 .gitignore 覆蓋。

取版本有兩條路，主用 GitHub REST API（額外給出官方 sha256 摘要，可校驗完整性）；實測未認證 訪問會按 IP 限流（撞到過 403），所以拿不到就退回不加 API 的 /releases/latest 302 重定向拿 tag ——這條路不消耗配額，代價是沒有官方摘要，只校驗檔案大小並告警一次。

下載下到哪兒都不會阻斷遊戲：拿不到新版就用手上這個舊的，一個都沒有就報「後端不可用」。 下載先落到 .download 暫存檔案，校驗通過才 os.replace 成正式 exe——不存在"半截 exe 被拉起" 的視窗。

指定了「實驗技術後端程式路徑」或環境變數 EF_CAPTURE_BACKEND 時完全跳過聯網：使用者自帶後端 就不該再去下載。同理「自動啟動後端」關掉時也不下載。

執行產物的保留策略

後端每局建一個 runs/<YYYYMMDD-HHMMSS>/，裡面是 capture.pcap + positions.jsonl （+ service.json），一局約 20 MB，不設上限能攢到幾個 GB。

我們拉起自己下載的那份時顯式傳 --runs-dir 指到 <托管目录>/runs，並在每次拉起探活成功 之後按「只留最近 5 局」清理一次。順序很關鍵：後端是先建目錄、再起 HTTP 服務的，所以埠應答 時新目錄必然已存在——放在 _launch 之後立刻清會早於它建目錄，穩態會留成 6 份而不是 5 份。

5.2 分層資源與樓層證據

與 nav-grid-editor 協作確認的 layers/catalog.json 當前使用 schema 1。 只將 map_category=layered 的圖層與對應 map_name 主圖共同定位；獨立場景不能僅憑歸檔目錄 推斷共享座標系，必須有自己的標定後再接入。圖層邊界按以下公式轉換：

X = west + u * (east - west) / width
Z = north - v * (north - south) / height

圖層會重取樣到 4 px/m，變換包含 OpenCV 畫素中心偏移。主層契約 ID 為 __main__。 視覺目錄 localization/layers/catalog.json 與導航層宣告索引是不同入口。導航從網格目錄 優先讀取 catalog.json，不存在時讀取資料倉的 levels.json；層 ID 須與網格後設資料的 tier 一致。目錄宣告不代表該層已有可走網格，缺少網格時仍須保留 no_grid 語義。 X/Z 相同但樓層不同的候選不能合併成一個樓層證據。樓層差距不足、相關資源缺失或目錄宣告 缺失樓層時，仍可接受有充分證據的水平位置，但必須釋出 tier_id=None、tier_trusted=False。 視覺源宣告 tier_evidence_required=True；網格導航在樓層未確認或沒有對應網格時拒絕猜主層。 抓包源有真實 Y，可繼續使用現有高度範圍和拓撲規則。不能把視覺未知高度補成零。

執行產物的保留策略

後端每局建一個 runs/<YYYYMMDD-HHMMSS>/，裡面是 capture.pcap + positions.jsonl （+ service.json），一局約 20 MB，不設上限能攢到幾個 GB。

我們拉起自己下載的那份時顯式傳 --runs-dir 指到 <托管目录>/runs，並在每次拉起探活成功 之後按「只留最近 5 局」清理一次。順序很關鍵：後端是先建目錄、再起 HTTP 服務的，所以埠應答 時新目錄必然已存在——放在 _launch 之後立刻清會早於它建目錄，穩態會留成 6 份而不是 5 份。

清理只動名字像時間戳的目錄（）。認不出的一律不碰：這個函式會刪東西，寧可漏刪 也不能誤刪使用者放在那兒的東西。時間戳定寬，所以字典序就是時間序。

使用者自帶的後端不加 --runs-dir——那會把它自己的產物挪到我們的目錄裡，屬越界。

順序是成敗關鍵：後端必須早於遊戲的主連線就緒，否則拿不到登入握手，後端會明確報 「缺少連線起點」而不是解出錯資料。

拉起的時機不能放在普通任務裡——任務要等遊戲視窗能截圖才會被執行（can_capture()）， 那時登入握手早就過去了。所以補丁包裝了 StartController.do_start，那是遊戲程序存在之前的 最後時機；WorldPoseService 的按需取樣會再兜底一次（後端中途掛了、或玩家在遊戲已經跑起來 之後才打開開關）。

直通模式下整條校準體系都不參與（座標本來就是絕對值，沒有錨點可設、沒有漂移可修）， 所以只要座標可用 sync_needed 就恆為假——否則導航的 CALIBRATE 狀態會停下來等一個永遠 不會到來的靜止校準。

會話邊界：座標是綁在一條 TCP 連線上的

「絕對」不等於「當前」。座標由某一條 TCP 連線解出，而那條連線會隨離開遊戲、換賬號、 重啟遊戲而結束。後端把最後一條座標一直留著（它的 state.last 沒有清空點），於是：

舊會話結束之後、新會話報出第一條座標之前，/api/state 給的仍是上一局的座標。

那可能是另一張地圖、乃至另一個賬號的位置。多賬號日常任務正好撞在這條路上： BaseEfTask.iter_multi_account_context 對每個賬號先調 login_flow，緊接著就跑送貨等導航任務。 切號的實際動作是離開遊戲再重新進入（login_flow 走 UI：退出到登入介面 → 選賬號 → 進入）， 而重新進入會建立新的 TCP 連線，所以每一輪切號都自帶一次"舊連線結束 + 新連線就緒"的交替。

這條對實現是有利的：切號不會複用連線，因此後端側那個"同四元組複用會讓 flow 永久失效" 的隱患在真實切號路徑上不會出現（見下文反面情形）。但它同時說明空窗期是真實存在且必然發生 的——遊戲退到登入介面、選賬號、再進入，這段時間裡 lastPosition 一直是上一個賬號的座標。

所以直通模式的信任是兩條一起判，任一不成立就不給導航用（_capture_trust）：

兩條都只扣信任、不清空座標：x/z 照給，讓導航停在 WAIT_TRUST 時能把真正的原因 打出來，而不是含糊地報「未錨定」。網路側資訊不足時（老版本後端不報 flows）一律當活著的 處理——缺資訊不等於會話已死，沒有證據就不扣信任。

導航等待態的文案會帶上 pose 裡的 trust_reason / odom_reason（形如 等待坐标: capture_unavailable），所以一眼能分清是「融合鏈還沒錨定」還是「抓包源沒資料」—— 這兩種情況該查的東西完全不同。

抓包模式不啟動小地圖定位鏈：start_minimap_position() 在本模式下直接返回， minimap_position_ready 也恆為真。兩處短路缺一不可——導航入口 （navigate_grid_to → ensure_runtime_position_service）會無條件調前者、緊接著檢查後者， 而抓包根本不需要比例尺/里程計/融合/地圖 WS。不短路的話有兩重代價：拿不到比例尺時導航會 立刻失敗並報一條指向全域性「導航配置」和遊戲視窗的錯（該查的其實是抓包後端）；拿得到時也會 白建兩個物件並啟動地圖 WS——正是本模式宣告要繞開的那一整套。

sync_seq 在抓包源上的含義是"座標基準變了"，不是"座標變了"：換連線時它一定推進 （連線的 id 參與判定），所以"登出後在原地重新登入"這種座標逐位相同的重登也會讓導航失效 已走過的已知格；而同一連線內怎麼移動都不推進。後者是必須的——導航把 sync_seq 變化當 "真重錨 → 世界座標整體平移"，抓包源移動時每拍座標都在變，若按"取樣變了"推進，移動本身就會 每拍清空導航的"走過的已知格"，偏航回退（網格導航文件 §7.5）會退化成"沒有已知格可返回"。

三類終態由兩條判據分別接住，缺一不可——後端的 snapshot 會把狀態計算覆蓋成 等待 TCP 补包（any(gaps) and not flow.failed 時頂替真實狀態），而收到 FIN 的連線並不是 failed，所以連線結束時若還有沒補齊的 TCP 空洞，它的終態就被遮住了：

  • 解码停止：… 只可能出現在 failed 時 → 覆蓋不生效 → 狀態判據接住（立即）；
  • 连接已结束 被空洞覆蓋遮住時 → 此時 lastPacket 已停止更新 → 30 秒靜默判據接住。

30 秒是個刻意偏松的值：誤判為「還活著」只是讓陳舊視窗變長，誤判為「已死」卻會把一條正常 連線的導航停掉；而活著的遊戲連線不會這麼久完全靜默（移動中約 0.27 秒一條，靜止時仍有其他 物件的報文）。代價是登出後最長 30 秒的陳舊視窗——但比改動前的「永久信任」已經是嚴格改善。

後端側還有幾條邊界值得記著（核實的是 endfield-capture-backend 的 decoder.py / server.py）：

  • 只抓 30000 / 40000 兩個埠。重登若換到別的埠，後端看不見那條連線，"自動接管新連線" 也就不成立；
  • flows[] 只回最近 12 條，更早的連線查不到——這也是"查不到即判死"的依據；
  • --seed-pcap 不是重登入的解法：它只能把同一條仍在使用的連線的金鑰流接上（所以 "上次 runs/ 裡的 capture.pcap"可用）。遊戲重啟換了連線後，重放出來的是另一條已經死掉的 連線，反而會解出一批陳舊座標；
  • 契約沒有任何版本欄位，也沒有 reset / 重連 / 健康檢查端點（/api/state 200 即探活， 應用側 probe_backend 用的就是它）；
  • 每次輪詢都會全量返回 trajectory（最多 1200 點，且跨連線混在一起）。應用側不消費它， 但會在 0.2 秒的輪詢週期裡反覆傳輸與解析——真嫌這個開銷，就換成後端的命名管道 （serve --pipe --no-http，事件驅動、不佔埠，欄位與 lastPosition 完全一致）， 應用側目前還沒接。

會話交替是自愈的：離開遊戲再進入會新建一條 TCP 連線

離開遊戲再重新進入（含多賬號切號）走新 TCP 連線。所以整條恢復路徑是順的，不需要任何額外處理：

离开游戏  → 旧连接收 FIN → 旧 flow 终态 → 应用扣掉信任（WAIT_TRUST），导航停车
重新进入  → 新连接 SYN → 后端按四元组新建 flow → 抓到新握手 → 报出新坐标
          → 新 flow 活着且地图认得出 → 信任恢复，导航接着走

關鍵在於後端不需要重啟：它按 TCP 四元組歸檔連線，新連線自然是一條新 flow， 只要後端還在抓包，新一輪握手就會被捕獲。這也是"預設不在停止定位時關閉後端"更有力的理由 ——後端的客戶端材料（DLL 私鑰、公鑰模數）是程序級的，會話 key/nonce 才是每連線現解的， 所以它可以跨掉線一直用下去。同理，應用側不需要在切號時做任何特殊處理（也不必去拉一次 後端）：do_start 若被再次呼叫，補丁只會探到後端已在跑並直接採用。

中間那段空窗期就是上面那條 capture_session_ended 生效的視窗：舊 flow 已經結束、新 flow 還沒報出座標，此時 lastPosition 仍是上一局的。視窗長度就是離開遊戲到重新進入的耗時。

反面情形（後端側尚未處理的邊界，實際不會碰到）：若遊戲複用同一條四元組發起新會話， 後端的 Reassembler.feed 只在基線為空時才接受 SYN，新明文握手會被當成加密幀、整條 flow 永久失效（重開遊戲才能恢復，重啟後端也沒用）。這種情況由 30 秒靜默判據接住。 真實的切號與重登都走新連線，所以這條不構成風險——但如果是用 kill_game 那種 TerminateProcess 強殺遊戲（危險狀態守衛、任務完成後勾選的「僅退出遊戲」走的就是它）， 對端來不及發 FIN，舊 flow 會一直停在「正在解碼」、lastPacket 也停更，這時只剩 30 秒 靜默判據在兜底，視窗內舊座標仍會被當成可信。

絕不要在遊戲執行期間重啟後端

比上面那條更硬的一條約束：會話金鑰由服務端在登入響應裡下發，每個賬號、每次登入都不同 （後端用客戶端內嵌的 RSA 私鑰從登入響應裡解出 32 位元組 key + 12 位元組 nonce）。所以 "重新登入"在協議上就是一次全新的握手，金鑰只在那一刻出現過一次。

推論：重啟後端不能解決任何解碼問題，只會製造問題——它把一個本來會被自動接管的局面 （新連線新握手）變成必須重開遊戲才能恢復（新後端看到的是一條沒有 SYN 的連線，只會報 缺少连接起点）。同理，「停止定位時關閉後端」開啟後如果應用在遊戲還開著時退出，下一次 開啟應用時後端雖然會被重新拉起，但當次登入已經救不回來了，只能重開遊戲。

應用側對這條約束的複查（結論：滿足）：

  • stop_capture_backend() 的生產呼叫點是 WorldPoseService.on_destroy()；
  • 服務銷燬由包裝後的 TaskExecutor.destroy() 觸發，而它來自執行器迴圈結束或 MainWindow.closeEvent，即應用退出，不會因為任務停用/重新載入/切號而觸發；
  • 真正殺程序還要 实验技术停止定位时关闭后端 為真，預設為假——所以預設連應用退出都不會 動後端（這也正是它預設為假的原因）；
  • 反之，ensure_capture_backend() 每拍都會走一遍，但它只會拉起、從不重啟已在跑的後端 （BackendLauncher.running 擋住重複啟動，健康期 5 秒內連探活都省掉）。

唯一殘留的坑是人為的：若使用者打開了「停止定位時關閉後端」，又在遊戲還開著時退出應用， 就必須重開遊戲才能恢復定位。這條已寫在那個配置項的說明裡。

校驗抓包是否真的接上了，沒接上就重建連線

座標缺失有好幾種成因，混在一起就沒法決定該做什麼——所以 CapturePositionSource.health() 把連線狀態單獨分類出來（CaptureHealth），只看連線、不看座標：

狀態 含義 該做什麼
ok / decoding 有座標 / 握手已成、座標在路上 正常
no_connection 後端在跑，但一條遊戲連線都沒看到 重建連線
handshake_pending 連線已發現，握手還沒完成 等
backend_down 後端不可達 查後端本身
missed_handshake 抓包晚於該連線建立 重建連線

判定口徑是"後端在跑、但當前沒有座標且不會自己恢復"：no_connection（這一局的位置源已經 沒了）與 missed_handshake（後端沒看到 SYN，推不出金鑰流）都屬於這一類，換一條連線讓它從頭抓 握手就行。handshake_pending（握手正在進行）再等一會就好，backend_down（後端根本沒起來） 重建也沒用——對它們動手只會白白打斷玩家。连接已结束（人家正常結束）與 解码停止（這條流真 出問題了）也不值得重建。

「一條死連線 + 一條活連線」必須判成正常：後端把歷史連線一直留著，拿舊的死連線判斷會讓 每一次正常抓包都被誤判成需要重建。

重建動作是回登入介面再進入（force_new_capture_connection），不切換賬號——使用者口徑是 "這個流程不需要重新選擇賬號"，所以不走會點「最近」、重選賬號的 login_flow。實際動作委託給 LoginMixin.relogin_same_account：回到主介面 → 點 main_out 登出入口 → 通用確認 → 回到登入 介面（這時能匹配到 fL.logout，遊戲顯示"點選任意位置繼續"）→ 點一下螢幕中央繼續進入。拿不到 可用的重進實現、或沒回到登入介面，都乾淨失敗並提示手動進入一次，絕不亂點。

登入介面的「最近 / 登入」按鈕仍只能走 click_text（login_ocr → login_screenshot，從螢幕 截視窗；普通幀通道在那種介面上取不到有效畫面）——那條路是 login_flow 切號用的，本重進流程 不用它。為此 WorldPoseService 混入了 LoginMixin（它沒有 __init__/default_config， 不會帶進「多賬戶模式」那套配置），重進直接用它現成的 relogin_same_account。

兩次重建之間至少隔 CAPTURE_RELOGIN_INTERVAL_SECONDS（20 秒）。ensure_capture_session 在 "沒座標"時每拍都會被調，沒有這個間隔三次嘗試會在一分鐘內打光——實測兩次只隔了 14 秒，而每次 都要把玩家從遊戲裡踢回登入介面。

三個時機都會校驗（ensure_capture_session）：啟用後第一拍、每次導航前、每次切號後。 最後一條值得說明：切號本身會重建連線、後端會自動接管（登入金鑰隨之重抓），不需要為它做特殊 處理——但"應該會發生"和"確實發生了"是兩回事，所以還是要校驗。

最多嘗試 3 次，成功即清零（重登後能正常抓包，下次再出問題理應還能修）；用盡就停手並 報錯——無人值守時反覆登出比不修更糟。可用「抓包失敗時自動重新登入」關掉。

首次使用建議盯一眼：重建動作依賴遊戲介面的特徵模板（登出入口 main_out、登入介面的 fL.logout）。版本不符時匹配不到，這一步會乾淨失敗並提示"請手動退回登入介面再進入一次"， 而不會亂點。這種情況把它關掉、手動退一次即可。

map_id 參與導航的換圖判定，而導航側算的是 str(pose.get("map_id") or session.request.map_id or "")——會靜默回退到呼叫方請求的地圖。 所以「認不出地圖」必須在定位源裡就扣掉信任，不能只靠導航自己判斷：實測場景 463 是自帶獨立 座標空間的可走區域（那 11 秒裡角色以 5.0 的速度正常行走，座標在 (16, 107, -41) 附近， 而 map02 的 y≈320、相距約 1400 個世界單位），拿它當 map02 會在錯的網格上、從錯的起點規劃 路線。這條與 _resolve_map_id 的「不猜」是同一條原則，只是貫徹到了 pose 的信任位上。

上報是事件驅動的：移動中約每 0.27 秒一條，完全靜止時沒有位置包，同圖傳送會有數秒到 數十秒的空檔。CaptureSample.age_seconds（後端 Unix 牆鍾減去當前牆鍾）因此只顯示不攔截 ——靜止時年齡大是正常的。它不進信任判定，它的用處是出現「座標跳變」或「導航拿著舊位置走」時 一眼看出資料來源當時到底有沒有在更新。後端跑在本機、需要 Npcap 驅動與客戶端檔案，屬於使用者自行 選擇開啟的功能（開關帶風險確認，見 src/patches/danger_switch_patch.py）。

6. 視覺鏈與時間

標定地圖的強匹配是絕對錨點，里程計給相鄰幀的相對位移。區域性視窗和關鍵幀圖使用視覺重疊邊 約束漂移，再將位置轉換回世界 X/Z；絕對錨點超過兩秒未重新整理時撤銷定位可信狀態。 載入、傳送、地圖變化和定位丟失不能延續舊視覺鏈。兩個來源都不要求導航停車等待 WS 校準， 釋出 sync_supported=False；sync_seq 只在座標基準改變時推進。

WGC 的 SystemRelativeTime 是 QPC 100 ns 時間，使用帶前後界限的本機時鐘觀察轉換到 UTC。 本機實測 WGC 回撥可能比其幀時間早數毫秒，因此允許最多 20 ms 的領先；保留原時間戳， 不平移或擬合延遲，超出領先界限或落後兩秒的時間戳拒絕使用。 時間戳關聯具體影像根陣列，保留幀在下一次截圖後仍可讀到原來的時間；不會給新幀套舊時間。 其他截圖方式或缺少後設資料時使用標明 sample_time_fallback 的接收時間，不能宣稱真實呈現時間。 frame_t 與 position_t 是 UTC；sample_t 仍為執行器活動時鐘，用於執行時快照新鮮度。

抓包時間是本機收包時間，仍可能與遊戲模擬和小地圖重新整理不同步。驗證僅在同一會話/場景且 相鄰包間隔不超過 0.5 秒時插值，不外推，不應用固定延遲補償。殘差同時包含地圖示定、 小地圖重新整理和收包延遲，不能稱為純視覺誤差。

7. 配置

全域性 Nav Config 的地圖 ID 是視覺搜尋的可選提示。地圖查詢介面的憑證繼續用於物品資源等業務， 生產定位不需要這些憑證，也不再讀取舊的 WS/手工軸對映標定值。

執行時引數儲存在全域性 Position Config：

  • 视觉地图资源目录；
  • 位移提交阈值(像素)；
  • 关键帧视觉锚定链校正 及其視窗、邊間隔、響應、錨點權重和修正上限；
  • 關鍵幀間隔、邊數、響應和區域性軟錨點權重。

退役的 WS 等待和航點靜止校準設定會在框架刪除舊鍵前備份到配置目錄下的 position_source_migration_backup/v1/Position Config.json。物品導航舊版實現選項與賬號覆蓋 遷移到“統一定位”，其他設定保留。

實驗技術（抓包直通，見 5.3）另有一組，預設關閉；開啟風險開關後才出現：

  • 使用实验技术：總開關，帶風險確認；
  • 实验技术后端端口：預設 8765，探活與拉起都用它；
  • 实验技术后端程序路径：留空則自動探測（託管下載目錄、同級 endfield-capture-backend/dist/、環境變數 EF_CAPTURE_BACKEND、PATH 等）。填了就完全 不聯網——使用者自帶後端；
  • 实验技术自动启动后端：預設開；
  • 实验技术停止定位时关闭后端：預設關。後端狀態綁在當前這一局連線上，關掉再拉起等於 丟了登入握手，必須重啟遊戲才能恢復；
  • 检查并更新后端：按鈕，立刻查一次更新（見 5.3「後端程式的獲取與更新」）。

解析度、來源、地圖資源或視覺鏈配置變化時，定位器重建並重新確認。

9. 除錯與測試

定位相關除錯任務位於 src/tasks/localization/：

  • MinimapRealtimePosition：逐拍檢視位置、來源、朝向、速度、匹配分數和樓層可信狀態；
  • MinimapPositionRecorder：逐拍落盤融合狀態、原始里程計位移、校準殘差和小地圖切片， 結束後生成 fused / odom 兩種畫素對齊拼接圖；
  • MinimapRegionCheck：檢查當前解析度下的小地圖環帶區域；
  • MinimapScaleCapture：採集靜止截圖與 WS 座標，用於比例尺標定；
  • MinimapTurnToHeading：驗證朝向讀取和轉向閉環。

取樣記錄的產物在 logs/minimap_position_recorder/<时间戳>/：samples.jsonl 是逐拍 資料，calibrations.jsonl 是每次靜止校準的殘差，patches/ 是 BGRA 圓環切片， stitch_*_fused*.png / stitch_*_odom*.png 分別是按融合座標和連續里程計軌跡拼接的 參考圖。需要換拼接引數時用：

uv run --locked python scripts/data-capture/stitch_minimap_recorder.py `
  logs/minimap_position_recorder/<时间戳>

常用測試：

uv run --locked python -m unittest tests.TestMinimapOdometry tests.TestMinimapPositionFusion tests.TestMinimapPositionMixin -v
uv run --locked python -m unittest tests.TestRuntimeStateHub tests.TestRuntimeStateMixin -v
uv run --locked python -m unittest tests.TestCapturePositionSource tests.TestCaptureBackendLauncher tests.TestCaptureBackendInstaller -v

定位異常排查順序：

  1. world.pose 是否存在且未過期；
  2. anchor_set 和 position_trusted 是否為真；
  3. odom_reason 是否長期不是 ok 或 shift_too_small；
  4. visual_confidence、visual_margin 和 tier_trusted 是否足夠；
  5. 資源目錄、mapping 尺寸和 map_id 是否匹配當前地圖。

視覺源冷啟動需要解碼基礎地圖，再檢查候選座標附近的重疊分層；layer_scan_pending 表示這次檢查尚未完整，不能提前釋出座標。若長時間迴圈出現 insufficient_acquisition_evidence，檢視 DEBUG 日誌 Visual acquisition rejected 裡的 ncc/full/margin/search_s，區分匹配證據不足與資源初始化耗時，不能當成正常預熱一直等。 這些拒絕診斷只記錄評分，候選座標仍不會作為可信位置釋出。

圖示遮罩由當前畫面生成，對所有候選使用同一套畫素，滿足覆蓋率、四象限和紋理檢查後 持續啟用。不能設定“圖示面積達到 10% 才啟用”的開關：圖示動畫跨過該邊界會讓整套遮罩 突然消失，導致同一地點從通過首次確認變成反覆全圖搜尋。首次確認仍要求嚴格匹配與連續兩幀。

開了實驗技術時改看這幾條：

  1. trust_reason 是不是 capture_unavailable——是就說明後端沒資料，先看後端本身；
  2. 後端日誌 logs/capture_backend/backend-<端口>.log：缺 Npcap 驅動、客戶端目錄不對、 「缺少連線起點」（抓包晚於登入握手，需重開遊戲或用後端的 --seed-pcap）都會寫在那裡；
  3. exe 沒下下來：看日誌裡那句「拿不到抓包後端的釋出資訊」（網路不通或 GitHub 介面被限流） 或「下載抓包後端 vX 失敗」。裝到哪兒了、裝的是哪個版本看 downloads/capture_backend/installed.json；點「檢查並更新後端」可立刻重試；
  4. capture_age 是不是一直很大——上報是事件驅動的，靜止時沒有新包屬正常，不攔截；
  5. trust_reason 是 capture_session_ended——座標還在，但它來自已經結束的一條連線 （離開遊戲、換賬號、重啟遊戲）。等新連線報出第一條座標即可自愈；一直不變就說明新連線沒解出來， 回去看第 2 條；
  6. capture_flow 是不是變了——切號會換一格，這是判斷「換了一局」最直接的現場資訊；
  7. capture_map_id_source 是 no_parent_map 或 capture_unknown_map——該場景沒有可用的導航 網格，導航會明確停車（前者是正確結果：試煉場這類場景本就不屬於任何大地圖，不是故障）。

日誌裡那句「還沒有解出角色座標」會自動分成兩種，因為它們的處理方式正好相反：

  • 一般情形 → 提示確認後端早於本局連線啟動；
  • flows[] 裡有一條停在「缺少連線起點」→ 直接提示重開遊戲，並說明重啟後端沒有用 （它看到的仍是一條沒有 SYN 的連線）。這條的典型成因就是後端被重啟過——而後端絕不該在 遊戲執行期間被重啟，見上文。
