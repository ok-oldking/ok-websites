Develop reusable Python automation through MCP

Quick start · Agent prompts · 中文入门 · 中文提示词

MCP connects your local coding agent to an ok-script application while it builds and tests reusable Python tasks. Spend model tokens on developing the script, then run the saved task through the application without the agent. Ordinary local recognition and input do not require LLM calls; later changes may need another development session.

The agent writes and edits project files, starts the local runtime, and reads logs and images through its filesystem tools. Use ok-script APIs and MCP for capture and interaction. Do not use Computer Use skills, plugins, or tools in this workflow.

Ask the agent to discover APIs and build a task

Connect to this project's MCP server. Call list_skills and read get_skill("develop"). Inspect the installed ok-script source and Python signatures for the APIs this task needs. Write a permanent Python task that opens Settings, enables "Show details", saves, and verifies the option remains enabled. Reset and verify the starting state before every attempt, save diagnostics, and test repeated runs through MCP. Register the finished task and provide its standalone run command without LLM calls.

MCP supplies skills and task execution, not a Python API catalog or get_api tool. Use the application's interpreter and inspect its installed package for exact signatures, docstrings, inherited methods, and return behavior. No library checkout is needed. See agent prompts for API-only discovery and existing-task repair examples.

The server's connection instructions direct agents to get_skill("generate-templates") before creating named image features: keep full screenshots and COCO annotations in ok_templates, export split features with generate_templates, and use find_feature/find_one in tasks. Those full screenshots can also be used directly as regression-test fixtures; get_skill("write-test") describes the test workflow. These instructions and skills come from the server's installed ok-script version.

Install and start

If the project has no environment or MCP runtime yet, start with the agent setup guide. Its setup skills can be read before installation, without connecting to a running server.

MCP is a required dependency of ok-script starting in 2.0.17. Install the capture and OCR profiles your project needs; no separate MCP extra is required. Use the project's virtual environment when one exists:

.\.venv\Scripts\python.exe -m pip install "ok-script[default]"
.\.venv\Scripts\python.exe -m ok mcp --config src.config:config

Use the application's existing requirements or lockfile when available and keep its chosen ok-script version. OpenCV remains a separate installation chosen by the application.

The default URL is http://127.0.0.1:8765/mcp. Use --port 8766 to change it, or --port 0 to choose an available port. If a requested port is occupied, the server tries the next port (+1) until it binds successfully, up to 65535. Other bind errors are reported immediately. The process stays running between attempts. Its regular task scheduler stays paused in this headless mode.

Starting a GUI for the same project replaces its registered console instance and closes that instance's MCP server. Use separate GUI and development entry points when the user-facing GUI should have MCP disabled. Close the GUI before starting another console development session.

To enable the same tools in the desktop application:

Open Settings > Basic Options > Enable MCP Server (off by default). Enabling it shows a security warning: connected agents can execute Python with your account permissions and read or change files. Confirming starts the server immediately; cancelling leaves it off. Turning it off, or resetting Basic Options, stops this instance's server immediately. The confirmed preference is saved for subsequent launches. If enabling from settings fails, the switch stays disabled and shows the error. Repair the project dependencies if the required MCP package is missing or incompatible.

You can also opt in explicitly from the command line:

.\.venv\Scripts\python.exe -m ok gui --config src.config:config --mcp

Applications using OK(config).start() can enable MCP through their config:

"mcp": {"enabled": True, "port": 8765, "artifact_directory": "logs/mcp"}

MCP artifacts use a seven-day retention period by default. Set mcp.retention_days to a nonnegative number of days, or 0 to disable cleanup. Cleanup runs on startup and at most once per hour when submitting runs/reloads or requesting screenshots. It removes expired completed run directories (including their logs, status and custom artifacts), their in-memory status records, and old observation images. Run age is measured from finished_at; observation age uses the image file's modification time. Active/nonterminal runs, unrecognized files and connection records are preserved. Copy evidence elsewhere if it must outlive retention.

The server binds only to IPv4 loopback and validates HTTP Host and Origin. Each instance writes logs/mcp/connections/<pid>-<port>.json containing its URL, bearer token, process ID, process start time and project directory. These records are removed when that server stops. logs/mcp/connection.json remains a compatibility snapshot of the most recently started server; it can be stale after that instance stops. Configure the agent's MCP client with the selected URL and the HTTP header Authorization: Bearer <token>. Set the environment variable OK_SCRIPT_MCP_TOKEN before starting the process if you need a stable token; otherwise a new token is generated on each startup. Treat this token as local developer access: task files execute Python with the process's permissions.

Discover running servers

Multiple projects can run MCP on the same PC: the first available port is reserved during startup, so instances cannot select the same port. Discover them from their project connection files instead of assuming port 8765:

from ok.core.mcp_server import discover_mcp_servers

servers = discover_mcp_servers([r'E:\projects\app-one', r'E:\projects\app-two'])
for server in servers:
    url = server['url']
    headers = {'Authorization': f"Bearer {server['token']}"}
    project = server['project_directory']

Omit the argument to discover servers for the current project. For a custom artifact directory, pass artifact_directory='logs/dev' (or an absolute path). Discovery reads per-instance records and the compatibility snapshot, removes duplicates, and checks process identity and ownership of the listening port. Missing, malformed and stale records are ignored. It does not scan ports or send network requests. Results contain credentials; keep them private. Distinct records also preserve multiple servers sharing an artifact directory. The application's existing single-instance policy for a project still applies.

Skill discovery

All exposed skills are for third-party applications using the library or MCP: application setup, task development and reloading, template assets, tests, and environment selection. They ship in the pip package with their supporting files and this guide. No library source checkout is needed. Skills discovered from a checkout and an installed release have the same consumer scope.

Call list_skills() for IDs, names, descriptions, resource URIs and absolute SKILL.md paths, then get_skill(skill_id) to read the relevant instructions. For example, use get_skill("develop") before implementing tasks. Relative links resolve from the returned local path. Repository commit, package release, and library translation maintenance are not exposed as skills or resources.

Clients supporting MCP resources can also discover these skills through resources/list and read ok-script://skills/<skill_id> through resources/read. Both interfaces return the same instructions.

Tools

Tool Arguments Result
list_skills None Available skill IDs, names, descriptions, URIs and local paths.
get_skill skill_id Skill metadata and full Markdown content.
list_tasks None Registered task IDs, names, absolute source paths, types and plugin ownership.
reload_tasks Optional task_ids list Immediately returns a run ID for reloading selected registered tasks, or all tasks/plugins when omitted.
run_task file_path Immediately returns a run ID, source hash and absolute artifact paths.
get_run_status run_id Execution state, phase, brief error and artifact paths.

States are queued, running, stopping, succeeded, failed, and cancelled. Only the last three are terminal. Run IDs are scoped to the current process; saved artifacts remain available after restarting it until retention cleanup.

Preferred workflow for existing tasks

Read the reload-tasks skill through get_skill("reload-tasks"). Use list_tasks() to find the existing implementation and its absolute source path, edit that file locally, then call:

reload_tasks(task_ids=["src.tasks.ExistingTask.ExistingTask"])
reload_tasks()  # All registered tasks and plugins

Use the exact task_id returned by list_tasks; display names and bare class names are not IDs. An empty list selects no tasks. Poll get_run_status(run_id) until the reload succeeds before testing. The record's operation is reload_tasks, and its result contains descriptors for the replacement tasks. Reload failures include an error and local run.log/status.json paths; existing task instances remain registered. A failure means subsequent execution would still use the old implementation.

Reloads compile the current task source without timestamp-based bytecode caches. Tasks sharing a module reload together; selecting any plugin task reloads its entire plugin, including pages and helper modules. Unselected task modules and helpers outside plugins stay cached. Restart the owned runtime after changing those helpers or adding new task registrations to the config. Debug mode does not watch or reload task files automatically.

Reloading does not call the automation's run(), reset the target application, or demonstrate success. Restore and verify the baseline before testing through the actual GUI task card or a thin run_task harness that calls the registered implementation with self.get_task_by_class(ExistingTask). Keep behavior changes in the existing task source instead of copying it into a temporary task.

File runs and reloads share the same active-run slot and exclusive executor ownership. Wait for the previous run and cleanup to finish before reloading. Reload requests stop scheduled one-time tasks and suspend triggers until completion; they do not restart stopped one-time tasks. stop_task can cancel a queued reload. Once the reload transaction starts, it finishes atomically; a successful commit reports succeeded even if a stop was requested meanwhile.

Execution ownership

Only one task file runs at a time. Each attempt acquires exclusive executor ownership: existing one-time tasks are stopped, and triggers are suspended until the attempt finishes. Stopped one-time tasks are not restarted automatically.

Cancellation is cooperative at framework sleep, capture and wait checks. A run marked stopping still owns the executor, including during cleanup. Code stuck in a blocking library or a Python loop without checks may require restarting the process. Wait for it to stop or exit before starting another process against the same application.

When idle, screenshot requests a fresh frame on the executor thread. During execution it saves the latest independent frame snapshot, without touching the capture backend from a second thread. Inspect cached and captured_at to judge freshness. Before the first captured frame it reports that no image is available. A task can call self.executor.next_frame() to update observations.

Exit and restart the runtime

Call exit_process(reason="Capture state cannot be reset") when runtime state cannot be cleared or reliably reset, a task remains stuck after cooperative cancellation, or changed configuration/imported helpers require a fresh process. It exits the ok-script process serving the current connection, including its GUI when present. It does not accept a target PID or restart the target application.

The tool returns {"state": "exiting", "pid": ..., "reason": ...} and schedules shutdown after a short delay to allow the response to reach the client. Repeated requests return the original acknowledgement. Normal runtime cleanup cancels active work and removes this server's connection record. A watchdog forces this process to exit after a five-second cleanup grace period (with an additional one-second fallback if shutdown diagnostics hang). Forced exit may skip task cleanup and leave incomplete artifacts or stale connection files; discovery ignores records for dead processes. A disconnect alone is not proof of exit.

Preserve available logs and screenshots before calling. Wait locally for the returned PID to exit, then relaunch through the project's existing development launcher and virtual environment. Rediscover the connection URL/token, since they may change. Run IDs belong to the old process; reconnect before submitting new work. Restore and verify the target application's starting state before testing again: restarting the runtime does not reset the target UI.

Task file contract

Each file defines a synchronous class Task(BaseTask) with these methods:

  1. reset_to_start() restores the application baseline. Reuse an existing recovery function when available. Make it safe to call when already at the baseline and after a partially completed attempt.
  2. verify_start_state() asserts the observable starting conditions or returns True. Returning False, another value, or raising blocks the main task. Returning None is supported for checks expressed as assertions.
  3. run() performs the automation and asserts its success conditions. Returning False or raising marks the attempt as failed.

The runner creates a fresh instance, calls after_init() and post_init(), prepares capture and interaction, then runs reset, verification and the task. It calls on_destroy() even if initialization, recovery or execution fails after constructing the task. Cleanup finishes before ownership is released. succeeded means the code completed without failure; include application-level success checks in run().

See the bundled examples/mcp_observe.py (source) for a runnable example. It captures the configured target without changing its state, so its reset is a no-op. For an interactive task, replace that recovery method and starting-state check.

Task code has the normal BaseTask API. For example, import an existing task's class and call self.get_task_by_class(ExistingTask).some_method() to reuse its functions. Registered project tasks are already available through the executor. Unregistered task classes need to be instantiated and initialized by your code.

Each invocation compiles the current task file directly, including same-size edits made within one second. Project imports and sibling imports are supported; use absolute imports for project packages. Shared imported modules remain cached in Python: restart the process after changing those dependencies. Task instances are temporary and do not appear in the regular task list.

Local evidence and the iteration loop

Each attempt writes logs/mcp/<run_id>/run.log and status.json. The run log captures executor-thread stdout, stderr, ok-script logging and the failure traceback. Background-thread messages remain in the application's normal logs. self.artifact_directory is a Path for additional per-attempt files.

Write useful diagnostics in the task itself:

self.log_info("Opening settings")
self.screenshot("before_settings")
# Perform actions, inspect the resulting UI, and assert the expected outcome.

Task screenshots use the project's normal screenshot directory and naming. They are saved asynchronously by the normal screenshot worker. The MCP screenshot tool returns only after its observation image has been saved under logs/mcp/observations/.

For existing tasks, the agent's loop is: discover the registered source, edit it, reload its task ID, wait for success, then run the registered implementation through a thin harness or the GUI and inspect local evidence. For new tasks, iterate on the submitted file before registering it in the project. Reset and starting-state verification run before every attempt, including the first one. Preserve failure evidence before the next reset. No MCP tools are needed for file editing or log reading. Use exit_process for runtime shutdown and local process tools to wait for exit and relaunch.

Run the finished automation without MCP

Register the permanent task in the application's configuration and ensure its normal execution path performs recovery and verification. MCP's reset hooks are not automatically called by the GUI or ordinary CLI. A temporary submitted file does not become a registered task.

After ending the development runtime, run the actual registered task name from the application directory, for example:

.\.venv\Scripts\python.exe -m ok run_task EnableOptionTask --config src.config:config

Alternatively, use the application's MCP-disabled GUI launcher. Keep the task module, configuration, recognition assets, and dependencies together. You can close the coding agent; return to it when the script needs changes.
